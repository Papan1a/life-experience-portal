# Issue #19 — Выбор аватара из предложенных + отображение

## Что нужно

В настройках профиля — возможность **выбрать аватар из набора предложенных** (готовых картинок). Выбор закрепляется за пользователем и отображается в разных местах (сейчас в фокусе — **топ-бар** и **профиль**).

## Решения, принятые при обсуждении

- **«Окошко онлайн»** из формулировки issue — это **отдельный будущий виджет**, которого ещё нет. Поэтому #19 **не трогает** блок «Что делают другие» и `FriendActivityDTO`. Аватары в онлайн-виджете — отдельная задача, когда виджет появится.
- **Хранение выбора:** пресет = статический файл `/images/avatars/{key}.png`; в `users.avatar_url` пишем его путь. Никаких новых полей/таблиц — переиспользуем существующее поле и `UserService.updateAvatar`. Загруженные через R2 (#12) и пресеты живут в одном поле единообразно.
- **Не зависит от R2/#7:** пресеты — статика, поэтому функция работает даже без настроенного хранилища.
- **Топ-бар:** аватар текущего юзера прокидывается глобальным `@ControllerAdvice` + `@ModelAttribute` (подгрузка из БД на каждый запрос) — всегда свежий, устаревание принципала не мешает.
- **Картинки-пресеты поставляет владелец** (кладёт файлы в `static/images/avatars/`). Инструкция фиксирует структуру и whitelist; имена файлов = ключам whitelist.

## Контекст (текущее состояние)

- Хранение: `users.avatar_url` (String); [UserService.updateAvatar](src/main/java/com/lep/portal/user/UserService.java) уже есть.
- Профиль: [user/profile.html](src/main/resources/templates/user/profile.html) / [profile.html](src/main/resources/templates/profile.html) уже показывают `${...avatarUrl} ?: default`. ✅
- **Топ-бар [_layout.html:87](src/main/resources/templates/_layout.html#L87)** — хардкод `@{/images/avatar-default.png}` (не показывает реальный аватар). ❌ чинить.
- Принципал [PortalUserDetails](src/main/java/com/lep/portal/user/PortalUserDetails.java) — `avatarUrl` не содержит (и не требуется при варианте с `@ControllerAdvice`).
- Профиль-редактирование: [user/edit.html](src/main/resources/templates/user/edit.html) — есть форма загрузки файла (`POST /profile/avatar`); галереи пресетов нет.
- Загрузка файла: [UserProfileController.uploadAvatar](src/main/java/com/lep/portal/user/UserProfileController.java#L114).
- Файлы: сейчас только `default-avatar.svg` и `avatar-default.png` — **набора пресетов нет**.

## Подход

### 1. Набор пресетов (файлы + whitelist)
- Владелец кладёт квадратные PNG в `src/main/resources/static/images/avatars/` (рекомендуется 256×256, единый стиль).
- Whitelist ключей — в `application.yml`, например:
  ```yaml
  app:
    avatar-presets: [cat, dog, fox, owl, panda, robot, cactus, mountain]
  ```
  Имя файла = `{key}.png`. Список читается в конфиг-бин (`@ConfigurationProperties` или `@Value`).
- Путь пресета: `/images/avatars/{key}.png`.

> Whitelist нужен не только для галереи, но и как **защита**: эндпоинт выбора принимает только `key` из списка, чтобы нельзя было записать произвольный путь в `avatar_url`.

### 2. Сервис
- Метод выбора пресета: проверить `key ∈ whitelist` → `userService.updateAvatar(userId, "/images/avatars/" + key + ".png")`.
- Размещение: пока — рядом с существующей логикой профиля. (При реализации #38 «AvatarService» этот метод переедет в сервис вместе с `uploadAvatar` — отметить связь, но не блокироваться на #38.)

### 3. Контроллер
- `POST /profile/avatar/preset` с параметром `key` → валидация по whitelist → выбор → `redirect:/profile/edit` с flash-сообщением.
- CSRF-токен обязателен (как в остальных POST-формах).

### 4. UI — галерея в `user/edit.html`
- Секция «Выбрать готовый аватар»: `th:each` по whitelist, каждая картинка — маленькая форма (`POST /profile/avatar/preset`, hidden `key`, кнопка-картинка).
- **Текущий** выбранный пресет визуально выделить (сравнить `user.avatarUrl` с путём пресета).
- Оставить рядом существующую загрузку своего файла (два способа: выбрать готовый / загрузить свой).

### 5. Отображение в топ-баре (с ОБЯЗАТЕЛЬНЫМ кэшем)
- Создать `@ControllerAdvice` c `@ModelAttribute("currentAvatarUrl")`, который для аутентифицированного пользователя возвращает `avatarUrl`, иначе `null` (см. null-safety в узких местах).
- В [_layout.html](src/main/resources/templates/_layout.html#L87) заменить хардкод на `th:src="${currentAvatarUrl} ?: @{/images/default-avatar.svg}"`.

**Кэш обязателен.** Топ-бар рендерится на каждой странице, поэтому наивный `UserRepository`-запрос в advice = +1 запрос к БД на **каждый** HTTP-запрос (включая HTMX-фрагменты). Это недопустимо — кэшировать `avatarUrl` по `userId`:

- Включить кэширование: `@EnableCaching` + простой `ConcurrentMapCacheManager` (in-memory достаточно — по архитектуре приложение работает на одном инстансе; см. `architecture_v1.md` §2).
- Метод получения аватара пометить `@Cacheable("userAvatars")` по ключу `userId` (метод в сервисе, не в advice — advice вызывает сервис).
- **Инвалидация во ВСЕХ точках записи `avatar_url`** — `@CacheEvict("userAvatars", key = userId)`:
  - выбор пресета (шаг 2 этой задачи);
  - загрузка файла [uploadAvatar](src/main/java/com/lep/portal/user/UserProfileController.java#L114) (#12);
  - любой будущий путь смены аватара.
- Без инвалидации сменённый аватар «залипнет» в кэше до перезапуска — это и есть главный риск, поэтому evict обязателен в каждой точке записи.

> При реализации #38 (`AvatarService`) и `@Cacheable`/`@CacheEvict` логично разместить в этом же сервисе — тогда все точки записи проходят через одну инвалидируемую границу.

### 6. Унификация дефолта (мелочь)
- Свести два дефолтных файла (`default-avatar.svg` и `avatar-default.png`) к одному — использовать единый fallback везде (топ-бар, профиль).

## Узкие места

- **`@ModelAttribute` на неаутентифицированных страницах** (login/register не используют `_layout`, но advice применяется глобально) — обязательно **null-safe**: если `principal == null`, вернуть `null`, не падать.
- **Оверхед БД на каждый запрос** (подгрузка avatarUrl в топ-бар) — закрывается **обязательным кэшем** (см. шаг 5: `@Cacheable` по `userId` + `@CacheEvict` во всех точках записи). Главный риск кэша — «залипший» аватар после смены, если забыть `@CacheEvict` хотя бы в одной точке записи. In-memory кэш рассчитан на один инстанс; при горизонтальном масштабировании — пересмотреть (общий кэш / инвалидация по событию).
- **Валидация `key` по whitelist** — без неё эндпоинт станет «записать любой путь/URL в avatar_url» (XSS/SSRF-риск в `src`). Это обязательно.
- **Синхронизация whitelist ↔ файлы**: ключ без файла → битая картинка в галерее. Инструкция: список в `application.yml`, владелец кладёт файлы с теми же именами. Можно добавить мягкую проверку при старте (лог-warning, если файла нет) — опционально.
- **Связь с #12/#38:** не дублировать; preset-выбор и upload — две точки записи в `avatar_url`. При #38 обе переедут в `AvatarService`.
- **Онлайн-виджет — вне scope** (отдельная задача): не трогать `FriendActivityDTO`/запрос друзей.

## Что НЕ трогаем

- `FriendActivityDTO` и блок «Что делают другие».
- R2/хранилище загрузки (#7) — пресеты от него независимы.
- Логику смены имени/пароля/email.

## Как проверить

1. В профиле есть галерея готовых аватаров; клик по пресету → аватар сохраняется, текущий выделен.
2. Выбранный аватар отображается в профиле и в топ-баре (на всех страницах).
3. Топ-бар больше не показывает хардкод-дефолт у пользователя с выбранным аватаром; у пользователя без аватара — единый дефолт.
4. Попытка `POST /profile/avatar/preset` с `key` вне whitelist → отклонена (аватар не меняется).
5. Неаутентифицированные страницы (login/register) открываются без ошибок (advice null-safe).
6. Загрузка своего файла (#12) продолжает работать рядом с выбором пресета.
