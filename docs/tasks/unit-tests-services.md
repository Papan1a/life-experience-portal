# Задача для DeepSeek: написать unit-тесты для сервисов

## Контекст

Проект — Spring Boot 3.4 + Spring Data JDBC + PostgreSQL, Java 21, Maven. Сейчас тестовый набор почти целиком **интеграционный**: большинство тестов поднимают полный Spring-контекст и реальную БД через Testcontainers. Это медленно и плохо покрывает ветвления логики.

Цель этой задачи — добавить **быстрые unit-тесты** на бизнес-логику сервисов: **без Spring-контекста, без Testcontainers, без реальной БД**. Зависимости (репозитории и другие сервисы) подменяются моками.

Не нужно дублировать то, что уже проверяют интеграционные тесты (HTTP-маршруты, рендеринг, реальные SQL-запросы). Тестируем именно логику внутри методов сервисов.

## Образец для подражания (ОБЯЗАТЕЛЬНО изучить первым)

В проекте уже есть правильный unit-тест: `src/test/java/com/lep/portal/user/UserServiceTest.java`. Он использует:
- `mock(...)` из Mockito для репозиториев и зависимых сервисов,
- ручное создание тестируемого сервиса через конструктор (`new UserService(...)`),
- `when(...).thenReturn(...)` для настройки моков,
- AssertJ (`assertThat`, `assertThatThrownBy`) для проверок,
- JUnit 5 (`@Test`, `@BeforeEach`).

**Все новые тесты должны следовать ровно этому стилю.** Никаких новых тестовых библиотек добавлять не нужно — Mockito, JUnit 5 и AssertJ уже доступны через `spring-boot-starter-test`. Не используй `@SpringBootTest`, `@Autowired`, `@MockBean`, Testcontainers — это unit-уровень.

## Что нужно покрыть

### 1. `ExperienceService` (`src/main/java/com/lep/portal/experience/ExperienceService.java`)
Самый важный кандидат — здесь много чистой логики. Новый файл: `src/test/java/com/lep/portal/experience/ExperienceServiceTest.java`.

Покрыть как минимум:
- **`setStatus(...)`** — три ветки: статус `null` → запись удаляется; запись уже существует → обновляется; записи нет → создаётся новая. Проверяй, что вызываются нужные методы репозитория и возвращается корректный результат.
- **`toggleBookmark(...)`** — две ветки: закладка есть → удаляется и возвращается `false`; закладки нет → создаётся и возвращается `true`.
- **`statusLabel(...)`** (обе перегрузки — для enum и для String) — что каждое значение маппится в правильную русскую подпись, и что `null` / неизвестное значение обрабатываются как описано в коде.
- **`getMyExperiences(...)`** — что результат сгруппирован по статусам в правильном **порядке отображения** и что пустые группы не попадают в результат. Это чистая логика группировки поверх данных из мока репозитория — её особенно стоит проверить.

### 2. `CatalogService` (`src/main/java/com/lep/portal/catalog/CatalogService.java`)
Новый файл: `src/test/java/com/lep/portal/catalog/CatalogServiceTest.java`.

Сосредоточься на методах с **логикой**, а не на простых делегатах к репозиторию (методы вида «вызвал репозиторий и вернул» тестировать на unit-уровне малоценно). Приоритет:
- **`getTagsByPrefix(...)`** — что пустой/`null`/пробельный ввод даёт пустой список без обращения к репозиторию, а нормальный ввод приводится к нижнему регистру и обрезается перед запросом.
- **`updateActivity(...)` и `updateVariant(...)`** — проверка прав: автор или админ могут редактировать, посторонний пользователь получает исключение (`ForbiddenException`). Это важная ветка безопасности.
- **`findOrCreateTag(...)`** — что существующий тег возвращается как есть, а отсутствующий создаётся с корректным slug (нижний регистр, trim).
- **`getCatalogPage(...)`** — логика выбора ветки (фильтр по тегам / по категории / без фильтра) и **расчёт количества страниц** (`totalPages`, `hasNext`/`hasPrev` в `CatalogPage`). Краевые случаи: 0 результатов → 1 страница.

### 3. `UserService` (`src/main/java/com/lep/portal/user/UserService.java`)
Дополнить **существующий** `UserServiceTest.java` (не создавать новый файл).

Сейчас покрыты `changePassword` и `changeEmail`. Не хватает:
- **`register(...)`** — основные ветки: email уже занят → исключение; happy path → пользователь сохранён и инвайт помечен использованным; гонка при пометке инвайта (`markUsed` вернул `false`) → исключение. Зависимости `InviteService` и `UserRepository` мокаются.
- **`changePassword(...)`** — добавить недостающую проверку: новый пароль короче минимальной длины → исключение (сейчас этот случай не покрыт).
- Проверь нормализацию email в `register` и `changeEmail` (trim + нижний регистр).

## Общие требования

- **Без поднятия Spring-контекста и без БД.** Только моки.
- Тестируй **поведение и ветвления**, а не приватные детали реализации. Один тест — одна проверяемая ситуация, имя метода описывает сценарий (как в образце: `changePasswordShouldFailWhenCurrentPasswordIsWrong`).
- Для русских строк-сообщений в исключениях проверяй текст так же, как в образце (`.hasMessage(...)`). Тексты бери из реального кода сервиса, не выдумывай.
- Не меняй production-код. Если метод невозможно протестировать как unit без изменения кода — **не трогай код**, опиши проблему в конце работы отдельным списком, чтобы человек решил.
- Не пытайся достичь 100% покрытия любой ценой: простые геттеры, делегаты-однострочники и DTO тестировать не нужно.

## Как проверить результат

Запускать только новые/изменённые unit-тесты, без поднятия всего набора:

```
./mvnw test -Dtest='ExperienceServiceTest,CatalogServiceTest,UserServiceTest'
```

Все тесты должны проходить, выполняться быстро (секунды, не десятки секунд) и не требовать запущенного Docker/PostgreSQL. Если какой-то тест требует контейнер — значит он написан неправильно (используется интеграционный подход вместо unit).
